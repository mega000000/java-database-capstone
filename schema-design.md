# Database Schema Design - Smart Clinic Management System

This document outlines the dual-database architecture used by the Smart Clinic Management System. We use **MySQL** for structured, relational data (such as users and schedules) and **MongoDB** for unstructured, document-based data (such as prescriptions and logs) that require flexibility.

## 1. MySQL Database Design (Relational)

### 1.1 Table: dmin
Stores system administrators who manage the clinic operations.
*   **id**: INT (Primary Key, Auto Increment) - Unique identifier for the admin.
*   **username**: VARCHAR(50) (UNIQUE, NOT NULL) - Admin's login name.
*   **password**: VARCHAR(255) (NOT NULL) - Encrypted password for authentication.
*   *Justification*: A simple, structured table for authentication where exact matches are necessary and relationships are minimal.

### 1.2 Table: doctor
Stores information about the doctors working in the clinic.
*   **id**: INT (Primary Key, Auto Increment)
*   **name**: VARCHAR(100) (NOT NULL) - Full name of the doctor.
*   **specialty**: VARCHAR(100) (NOT NULL) - Medical specialty (e.g., Cardiology, General Practice).
*   **available_times**: VARCHAR(255) - Working hours/shifts representation.
*   *Justification*: A core relational entity that will be frequently queried and linked to appointments.

### 1.3 Table: patient
Stores patient profiles and contact details.
*   **id**: INT (Primary Key, Auto Increment)
*   **name**: VARCHAR(100) (NOT NULL) - Full name of the patient.
*   **email**: VARCHAR(150) (UNIQUE, NOT NULL) - Email address for contact.
*   **address**: VARCHAR(255) - Physical address of the patient.
*   *Justification*: Patient data is highly structured and must maintain consistency across appointments and reports.

### 1.4 Table: ppointment
Manages scheduling and links doctors to patients.
*   **id**: INT (Primary Key, Auto Increment)
*   **doctor_id**: INT (Foreign Key -> doctor.id, NOT NULL)
*   **patient_id**: INT (Foreign Key -> patient.id, NOT NULL)
*   **appointment_date**: DATE (NOT NULL)
*   **appointment_time**: TIME (NOT NULL)
*   **status**: VARCHAR(20) (DEFAULT 'SCHEDULED') - e.g., SCHEDULED, COMPLETED, CANCELLED.
*   *Justification*: This is a classic intersection/transaction table resolving the many-to-many relationship between doctors and patients. Relational constraints ensure referential integrity.

## 2. MongoDB Collection Design (Document-based)

### 2.1 Collection: prescriptions
Prescriptions can vary widely in structure, sometimes requiring multiple medications, dosages, embedded notes, or doctor instructions. MongoDB is ideal for this flexibility.

**Document Schema Design & Constraints:**
*   _id: ObjectId (Primary identifier generated by MongoDB).
*   ppointmentId: Integer (Reference to MySQL appointment.id to tie relational and document data).
*   patientName: String (Denormalized for faster read queries).
*   medication: Array of Objects (Allows multiple drugs, dosages, and frequencies).
*   
otes: String (Optional free-text field for doctor's observations).
*   createdAt: ISODate (Timestamp for when the prescription was issued).

**Realistic JSON Document Example:**
\\\json
{
  "_id": { "": "64fb5c8e2b8c9a3d4e5f6g7h" },
  "appointmentId": 105,
  "patientName": "John Doe",
  "medication": [
    {
      "name": "Amoxicillin",
      "dosage": "500mg",
      "frequency": "Twice a day",
      "durationDays": 7
    },
    {
      "name": "Ibuprofen",
      "dosage": "200mg",
      "frequency": "As needed for pain",
      "durationDays": 5
    }
  ],
  "notes": "Patient advised to take antibiotics with meals. Follow up if symptoms persist.",
  "createdAt": { "": "2026-09-21T09:30:00Z" }
}
\\\

*Justification*: By using a document store for prescriptions, doctors can add varying amounts of details (multiple medications, complex dosage instructions, follow-up advice arrays) without needing a complex set of joined tables (e.g., prescription_drugs, prescription_notes). Denormalizing patientName avoids an extra cross-database query when generating patient views.
